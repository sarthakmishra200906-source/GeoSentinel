# GeoSentinel Simulation and Live-Map Verification

**Updated:** 2026-11-15  
**Latest verification:** simulation report archiving, global custom routes,
admin live-map navigation, and responsive navigation layout

## 1. What an admin sees now

The admin workspace has separate Overview, Simulation, Operations, Guidelines
& upload, Audit log, and Live cyclone map sections in the side navigation.
The map uses the same WindyMap component and live-data source as the user map.
The Rain/Heat/weather controls sit clear of the sidebar on desktop and below
the mobile menu toggle on small screens. There is no separate cyclone-feed
status widget.

The admin has distinct data experiences:

### Simulation workspace

Open:

```text
Admin dashboard -> Simulation
```

This view shows the selected synthetic cyclone run:

- Scenario name and a custom 2–20 waypoint route, with latitude/longitude
  inputs and map-click route insertion.
- Approach distance, wind speed, rainfall, duration, institutions, and
  shelters.
- Create run, step one synthetic hour, and pause controls.
- Synthetic cyclone path map with current position and target corridor.
- Timeline slider plus previous/next-hour replay.
- Hourly charts for risk, rainfall, river signal, river-discharge proxy, and
  temperature proxy.
- Odisha district evidence for 30 districts.
- Synthetic India-wide context for 36 states and union territories.
- Reference-only rescue-center markers for registry entries in open or limited
  status. The latest local registry query returned zero such centers, so the
  empty state was verified but populated-marker rendering was not.
- Peak risk, peak rainfall, peak river proxy, and response-resource advice.
- Explicit user-help/SOS status.
- Explicit AI insight status.
- Three downloadable data reports: executive JSON, hourly CSV, and India-state
  CSV.
- A complete server-generated PDF archive that admins can preview and download.

The outcome pack says clearly that the run is synthetic. It does not present
synthetic values as live gauges, official forecasts, real citizen reports, or
AI forecasts.

### Live cyclone map

Click:

```text
Admin dashboard -> Live cyclone map
```

This keeps the admin workspace navigation visible while rendering the same
normal live Windy map used by users. It uses the GDACS live-event endpoint and
does not render a simulation route. A provider outage is shown as unavailable
and clears stale markers; it must not be interpreted as proof that no cyclone
exists.

### Operations, Help, and grounded guidance

The Operations view includes the admin Help requests inbox, which displays
submitted requests with their status, location/map link, and authorized image
preview when available. It is separate from the simulation: a synthetic run
does not create help requests or change rescue-center records. The latest
local check displayed one existing pending request; personal details are
intentionally omitted from this handoff.

The Guidelines & upload view separates approved and pending documents. Grounded
chat retrieves only approved document chunks and shows source citations. A
local test returned a `GROUNDED` answer with citations to the approved
`Disaster Management Plan SSD Department`. The test question was run outside
an active simulation; no simulation data was added to RAG.

## 2. Can an admin view and download the summary?

Yes. The summary is visible in the Simulation workspace after at least one
synthetic step. It contains the current selected hour and peak-run values.

The three report actions are:

1. **Executive summary JSON**
   - Scenario and run metadata.
   - Peak and viewed timestep.
   - User-help isolation status.
   - AI insight status.
   - Explicit limitations.

2. **Hourly telemetry CSV**
   - One row per generated hour.
   - Risk, rainfall, river signal, river-discharge proxy, temperature proxy,
     wind, and cyclone distance.

3. **India state impacts CSV**
   - One row per state/union territory per generated hour.
   - State risk, rainfall, river proxy, temperature proxy, and synthetic
     provenance.

The JSON/CSV exports are generated in the admin browser from the selected
run's stored timestep data. A separate complete PDF is generated by the
backend and stored with the run in MongoDB. The report includes all recorded
hours and the district/state evidence. Its SHA-256 digest is returned in
metadata and in the `X-Report-SHA256` response header.

The backend exposes these admin-only evidence endpoints:

```text
GET /api/simulation/runs/:id/report
GET /api/simulation/runs/:id/reports
POST /api/simulation/runs/:id/reports
GET /api/simulation/runs/:id/reports/:reportId/pdf
```

The PDF can be returned inline for preview or downloaded with `?download=1`.
Runs that complete at their configured duration get a PDF automatically;
admins can also request one after at least one timestep. PDF data is capped at
12 MiB per MongoDB document to remain below BSON's document limit. This is
durable within the configured MongoDB deployment, not object storage or a
cryptographic signature. Backups, retention, and production object storage
remain deployment work.

## 3. What happens when another cyclone is tested?

Each click of **Create test run** creates a new scenario and a new
`SimulationRun`. Its custom route and parameters are stored separately. Every
step is stored as an immutable `SimulationTimestep` with a sequence number.

The Simulation workspace now has **Saved cyclone runs**. An admin can:

1. Create a new cyclone with different coordinates, wind, rainfall, or
   duration.
2. Advance that run.
3. Select an older run from the saved-run selector.
4. Reload its stored hours, map, timeline, district table, state table, charts,
   and reports.
5. Use the run ID to retrieve its backend evidence report.

The currently selected run ID is remembered in the browser tab's
`sessionStorage`. Leaving Simulation for **Live cyclone map** or **Operations**
unmounts its panel, but returning now reloads that run and its stored
timesteps/reports. Navigation does not advance synthetic time: use **Step +1
hour** to advance it. The run and timesteps remain persisted in the backend.

The run list is cursor-paginated in pages of 50. A selected run reloads up to
168 stored timesteps. Long-term production work still needs server-side search,
retention, labels/tags, and object-storage report artifacts.

## 4. Custom cyclone route and impact behavior

The scenario inputs support 2–20 global waypoints, with latitude from -90 to
90 and longitude from -180 to 180, as well as:

- Wind speed.
- Rainfall per hour.
- Rain duration.
- Exposed institutions.
- Available shelters.

The simulator interpolates along each leg of the custom route, including the
shortest path across the international date line. The selected hour controls
the displayed map, charts, district results, state results, and resource
advice. Custom routes change cyclone movement only: detailed impact output
remains an Odisha-only synthetic district model plus synthetic state context.

The impact engine is intentionally a bounded rule matrix. It uses rainfall,
river signal, soil saturation, cyclone wind, and exposure heuristics. It does
not calculate official cyclone track uncertainty, storm surge, cell-level
inundation, building damage, exact road closure, or gauge-calibrated flood
depth.

## 5. Are simulation results visible to ordinary users?

No, not through the current application flow.

- Simulation API routes use `requireAdmin`.
- Scenario creation, run listing, run loading, stepping, pausing, heartbeat,
  and report retrieval are admin-only.
- The normal user-facing `MapContainer` is not passed simulation state.
- The normal user map is rendered when the application is not in the admin
  view.
- The synthetic run is not written to live notifications, SOS, reports,
  dispatches, live weather, or RAG documents.

This means a normal user does not see an admin's test cyclone by default.
An approved future feature could allow explicitly authorized simulation
viewers, but that is not enabled.

## 6. Does the admin normal map show simulation data during a run?

No. The current behavior is deliberately separated:

- **Simulation tab:** synthetic cyclone path and synthetic impact data.
- **Live cyclone map tab:** normal live Windy/GDACS map behavior.

The browser verification performed this transition:

```text
Simulation view: present before Map click
Click Live cyclone map
Simulation element: absent
Admin workspace navigation: present
Normal map controls: present
Synthetic cyclone layer in normal map: not present
```

The simulation does not leak into the normal map. When the admin returns to
Admin dashboard -> Simulation, the saved run can be selected again.

## 7. Does the synthetic cyclone disappear after the test?

It disappears from the normal map immediately when leaving Simulation because
the normal map never consumes simulation state. The saved run itself is not
deleted. It remains available to the admin through Saved cyclone runs and the
admin-only report endpoint.

This is the intended distinction:

- **Disappear from live/public map:** yes.
- **Destroy the admin's evidence:** no.
- **Create a live alert automatically:** no.
- **Make an ordinary user see the test:** no.

## 8. What would happen during a real live cyclone?

The normal map would continue to use its live weather/cyclone behavior and
would not use the synthetic simulation path. Live cyclone visibility depends on the configured live provider and its
timestamps, quotas, errors, and data availability. During the latest browser
check, GDACS returned an unavailable status, so live event ingestion was not
verified; the map displayed no markers, which is not evidence that no cyclone
exists.

The simulation does not automatically predict or publish a real cyclone. The
simulation is for rehearsal. A real operational alert requires the separate
live-provider, notification, SOS, operator, and AI/RAG workflows to be
validated.

The local tests did **not** prove:

- A real cyclone provider event arriving during a simulation.
- 10,000 users viewing a live cyclone simultaneously.
- 10,000 AI conversations.
- Real SMS/email/push delivery.
- WebSocket/SSE fan-out.
- Live SOS/help workflows under cyclone load.
- Cloud failover or provider quota recovery.

## 10. Current readiness statement

The system has working **admin-only local synthetic rehearsal, saved-run
review, route editing, per-run stored PDF preview, Help inbox visibility, and
grounded retrieval from approved guidance**. Automated and visual checks do not
establish end-to-end API persistence, provider reliability, or production
readiness.

It is not ready to claim:

- Official forecasting.
- Live emergency command.
- Public simulation sharing.
- Immutable/tamper-evident PDF storage (the MongoDB document and checksum do
  not constitute a digital signature).
- 10,000 concurrent full-system users.
- Complete live cyclone + AI + SOS + notifications integration.
- Deployment-grade retention, backup/restore, and object-storage behavior.

Those limitations are intentional and must remain visible to evaluators.
